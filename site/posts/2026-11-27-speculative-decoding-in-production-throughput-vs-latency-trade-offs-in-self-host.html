Speculative Decoding in Production: Throughput vs. Latency Trade-offs in Self-Hosted LLMs

Moving speculative decoding past the benchmark suite requires treating the draft-target loop as a constrained distributed systems problem over tensor memory.

For a self-hosted LLM platform running 70B+ parameter models on clustered accelerators, the primary operational bottleneck is not compute—it is memory bandwidth during the autoregressive generation phase. Every single token generated requires streaming the entire weight matrix of the target model from High Bandwidth Memory (HBM) to the SRAM of the compute units.

Speculative decoding bypasses this memory bottleneck by using a lightweight draft model to generate $K$ candidate tokens in a fraction of the time, followed by a single parallel forward pass of the large target model to validate them. While academic literature routinely reports 2x to 2.5x speedups, deploying this in production introduces severe tail-latency cliffs, GPU memory fragmentation, and GPU scheduling overheads that break naive implementations.

Constraints & Target Workload

Assume a self-hosted inference cluster running a Llama-3-70B-Instruct target model sharded across 4x NVIDIA H100 (80GB) GPUs using Tensor Parallelism (TP=4) over vLLM. - Workload Profile: Mixed enterprise API traffic combining chat completions (short prompt, medium output) and batch summarization (medium prompt, long output). - Service Level Objectives (SLOs): Time to First Token (TTFT) < 200ms; Time per Output Token (TPOT) < 30ms at p99. - Hardware Constraints: 100% HBM utilization under peak load. Adding a draft model (e.g., Llama-3-8B) on the same GPU nodes increases memory pressure and risks out-of-memory (OOM) errors during KV-cache dynamic allocation spikes.

System Design: Co-located vs. Disaggregated Draft Execution

The architectural choice for speculative decoding comes down to where the draft model executes: co-located on the same accelerator pool or dislocated across separate hardware.

[Incoming Request] 
       │
       ▼
[vLLM Engine (TP=4)] ──(KV Cache Sync)──> [Draft Model (Llama-3-8B)]
       │                                         │
       └───────► [Target: Llama-3-70B] ◄─────────┘
                   (Parallel Verification)

In a co-located design, the draft model shares the HBM of the target model's accelerators. This eliminates network serialization overheads for token handoff, but it exacerbates KV-cache fragmentation. The vLLM PagedAttention allocator must reserve fragmented memory blocks for both models, reducing the maximum concurrent batch size (max_num_seqs).

If the draft model is hosted on a separate smaller GPU instance (e.g., an L4 or T4), IPC (Inter-Process Communication) and gRPC/RDMA serialization overheads for token streams can easily consume 5ms to 10ms per step. For a target model where a single decoding step takes ~12ms, a 7ms network round-trip entirely negates the speculative speedup.

Therefore, production-grade deployment for high-throughput, low-latency APIs demands a co-located, in-process draft execution loop where KV-cache management is unified.

Args:
    target_logits: Tensor of shape [batch_size, k + 1, vocab_size] from target forward pass.
    draft_tokens: Tensor of shape [batch_size, k] containing tokens generated by draft model.
    draft_probs: Tensor of shape [batch_size, k, vocab_size] containing draft token probabilities.
    temperature: Sampling temperature. 0.0 implies greedy decoding.

Returns:
    accepted_tokens: Tensor of shape [batch_size, <= k + 1] containing valid tokens.
    num_accepted: Integer count of accepted tokens for metrics emission.
"""
batch_size, k_plus_one, vocab_size = target_logits.shape
k = k_plus_one - 1

if temperature == 0.0:
    # Greedy decoding path
    target_tokens = torch.argmax(target_logits, dim=-1) # [batch_size, k + 1]

    # Match draft tokens against target argmax
    match = torch.cat([
        (draft_tokens == target_tokens[:, :-1]),
        torch.ones((batch_size, 1), dtype=torch.bool, device=target_tokens.device)
    ], dim=1) # [batch_size, k + 1]

    # Find the first mismatch per sequence
    match_int = match.to(torch.int32)
    cumulative_match = torch.cumprod(match_int, dim=1)
